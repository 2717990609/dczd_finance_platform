# 财务平台

财务工作台提供产品目录、来源映射、期次、产品规则、组织人员、来源订单、分润试算和结算核对。后端使用 Go、go-zero 和 PostgreSQL，前端使用 Vue 3、Vite 和 Ant Design Vue。

财务平台独立部署，使用独立数据库。正式启用后，本平台是财务业务的唯一办理入口。产品规则、组织任职、账号权限、核算、结算和差额处理均在本平台维护。各业务子系统维护订单、退款、报名和签到，财务按需主动读取。

授权配置人员在「产品规则」保存并生效。试算从本平台数据库按产品、业务场景、账期或班次匹配适用规则。计提和结算保留实际使用的规则版本，后续退款或更正可在本平台回查。核对过的配置文件可用于一次性初始化。验收与正式运行只配置本平台数据库及所需业务子系统。

日常在「产品目录」维护产品和来源映射，在「组织与人员」维护任职，在「产品规则」配置分项和生效范围。在「分润试算」选择核算期，核对原订单、适用规则及分润明细后办理结算，再到「月度汇总」查看公司、部门和人员的结果。订单、退款、报名或签到有误时，在对应业务子系统更正，再回到本平台重新拉取和核算。

工作台、操作提示、报表和导出统一使用本平台的业务名称。配置入口使用「产品规则」，期次使用「适用规则」，核算明细显示「订单版本」和「规则版本」。查询历史结算时，显示实际计提所用的规则名称与版本。初始化清单中的产品及规则显示名称也使用这些业务名称。

| 目录 | 内容 |
| --- | --- |
| `server/` | Go 模块、路由、数据库结构与后端测试 |
| `web/` | Vue 页面、表格与配置表单 |

## 正式启用验收

- 使用正式环境的独立数据库和财务账号，服务端只配置所需的业务子系统接口。核对产品、场景、生效的规则版本、组织任职和权限。
- 核对承接范围内的历史结算及其订单、规则与归属引用，并确认实战班累计期初、团队池余额、待处理退款和差额。用确定的账期和同步水位核对首期的订单范围和金额，防止漏算或重复计提。
- 以财务账号完成规则生效、主动拉取、草稿试算、正式结算及历史查询。确认工作台、报表和明细使用本平台的产品名称、适用规则和规则版本。分别验证固定账期和实战班签到期次，核对公司、部门和人员报表。来源数据更正后重新拉取，核对差额进入可办理账期及原正式结果的完整性。
- 正式启用前逐产品确认已结算业务范围、首个办理账期或班次、来源同步起点和启用时间。在相同截止时点核对末期结算与首期试算的业务范围，确保每笔付款只计提一次，未办退款和差额可继续处理。
- 自约定的启用时间起，财务在本平台办理产品配置、规则生效、试算、正式结算、汇总及差额处理。业务人员在对应子系统更正订单、退款、报名或签到后，财务在本平台重拉并处理。

## 首次初始化

在启动工作台前准备独立 PostgreSQL 数据库。使用实际目标库设置 `FINANCE_DATABASE_URL` 和 `FINANCE_EXPECTED_DATABASE`，并在连接中设置一个空应用 schema。空数据库通常使用默认的 `public`。正式环境使用 `FINANCE_ACCESS_MODE=managed`。

初始化清单是一个 JSON 文件，包含以下字段。各配置对象使用「产品与数据配置」中的格式。

| 字段 | 内容 |
| --- | --- |
| `database` | 目标库名，与实际连接的数据库相同 |
| `schema` | 可选。默认为 `public`，指定其他名称时须与连接实际使用的应用 schema 相同 |
| `productConfig` | 产品目录、来源场景和规则版本配置 |
| `organization` | 人员、组织树、任职及可选的来源公司映射和推荐关系 |
| `salesContext` | 可选。使用大春 AI 核算时附带所需的人员、公司、销售类别和计提任职配置 |
| `practiceOpenings` | 可选。实战班冻结累计期初数组。每项用 `productCode` 指向本清单内的产品，其余字段为 `sourceSettlementId`、`throughAt` 和 `people` |

```sh
go -C server run . initialize-finance /secure/finance-initialization.json
go -C server run . initialize-finance /secure/finance-initialization.json --apply
```

第一条命令验证完整导入并回滚。第二条在一个事务中提交，任一步失败都会回滚。在成功后重试同一文件会返回已初始化。已有业务数据的环境通过对应的日常维护或迁移流程更新。

初始化后使用 `configure-finance-account` 登记账号和产品权限，按验收范围配置核算期次、班次规则和来源同步。产品结算默认关闭，按对账结果逐个启用。历史正式结算及其中的资金池余额按下文承接。

## 历史结算承接

用目标产品已确认的归档资料回放历史期次。核对归档订单和退款版本、当时的规则、组织归属、实战班名单及团队池实际分配。日常结算开放前，按同产品原确认时间依次承接，资金池余额由已承接流水结转。历史承接适用于能在目标库逐笔对平的期次。

`adopt-finance-history` 读取一个期次的 JSON 清单，填写 `database`、`schema`、`productCode`、`periodId`、带时区的原 `confirmedAt` 和 `expected`。`expected` 包含净业绩 `performanceMinor`、计提 `accruedMinor`、退款 `refundMinor`、更正 `correctionMinor` 和各自的 `performanceCount`、`accrualCount`、`refundCount`、`correctionCount`。金额单位为分，退款扣减填负数，计数为保存的明细行数。

1. 运行 `--rows` 输出对账明细。逐项核对原始订单、规则、金额、归属、受益人及资金池分配。核对通过后，将该文件的 SHA-256 写入清单的 `postingsSha256`。
2. 运行只读试跑，核对返回的金额、笔数和草稿版本，将返回的 `reviewToken` 写入清单。标识绑定当前数据库实例、草稿、名单和分配。
3. 带 `--apply` 提交。系统复验并按原确认时间冻结，使用新连接回读结果。同一清单重试返回同一结算。财务可在「月度汇总」按已结算查询，后续退款引用原计提和受益人。

```sh
umask 077
go -C server run . adopt-finance-history /secure/history.json --rows > /secure/history.ndjson
shasum -a 256 /secure/history.ndjson
go -C server run . adopt-finance-history /secure/history.json
go -C server run . adopt-finance-history /secure/history.json --apply
```

## 核算与报表

规则版本保存分项、费率、适用范围及来源角色。订单修订各保存一次，试算明细引用订单、人员归属和规则版本。

本地工作台可配置自然月和 25–24 等固定账期，试算销售及推荐提成，查看唯一最新草稿和待核项。固定账期按上海时间划分，人员归属按实际付款时点读取。同一核算范围、规则和财务结果重复试算时沿用当前草稿。「业绩与分润」按当前草稿或已确认版本查看人员、公司和部门汇总。订单业绩按订单发生时的销售归属统计，分润按受益人归属统计，退款按原付款归属冲减。未能唯一匹配的归属显示为「归属待核」。

「月度汇总」可查看单个或全部产品，按公司、部门或人员查看净业绩、分润、退款、更正和资金池分配。可选择当前结果或仅已结算结果。当前结果显示各核算期的试算状态。固定账期及退款账期按登记月份汇总，开班期次默认按结束日期归月，开放期次可在「核算期次」指定报表月份。报表月份只用于汇总。重复且金额与归属一致的付款或退款只计一次业绩，冲突时显示待核。同一查询翻页时校验结果版本，变化后提示刷新。

订单核算字段、规则、人员归属或签到名单有变化时，系统标记受影响的开放期次。自动试算默认每 30 分钟扫描一次，更新同一份草稿且跳过未标记的期次。订单展示信息变化只保存订单版本。工作台显示待试算状态，也可手动重新试算。已确认的结算使用保存时的结果及规则版本。开发环境可通过 `FINANCE_DRAFT_REFRESH_INTERVAL` 调整扫描间隔，设为 `0` 时只执行手动试算。

大春 AI 固定账期试算复用输入一致的逐单分润，只对受影响的付款重新计算分项。每次仍核对适用订单、退款和业绩归属，生成完整的最新草稿。规则或配置变更时整期重算，实战班按整期计算名单与阶梯。逐单计算结果只在服务进程内暂存，重启或超出缓存容量时整期计算。正式确认独立计算整期，再与最新草稿核对。

保存时保留内容和来源版本一致的计提明细，只写入新增或变化的普通明细并移除失效行。资金池计提内容或顺序变化时，按本次计算顺序重建该期的资金池明细。

固定账期按付款时点选规则版本，实际开班按子系统确认名单中的开班时点选整期规则。指定期次优先于起始期数，起始期数优先于产品默认。固定账期内不同付款可以匹配不同版本，实际开班一期共用一个规则版本。

「核算期次」遇到名单开班时间超出所登记日期时显示待核状态。已结算班次显示确认时使用的名单开班时间和规则版本，便于与结算明细对照。

实战班试算关联来源期次标识，由已确认签到的最新名单决定纳入哪些报名。新报、复训可配置不同销售或推荐分项。订金和尾款按一份报名计算，个人销售和推荐按净实收分摊。仅签到的赠送或兑换报名计入到课人数。延期后，开放期次以各自最新确认名单重算。同一付款仍在两个开放期次时，两边都列为待核。报名中任何一笔付款已正式入账时，目标班将这份报名列为待核，其他报名继续试算。该付款的退款按已确认的结算及退款账期处理。技术人员删除错账后，受影响的开放班次和累计阶梯草稿重新试算。

实战班的新报个人销售支持累计人数、本期实付和人数优先三种阶梯。累计可以从期数或开班时间起算。可在同一规则版本内为个人单独设置起点，切点到达后重算该人员的累计。档位可配置上下限、比例或固定额。可以按来源订单中的销售公司配置不同档位。同一人的累计人数与选档业绩合并统计，销售公司选项从数据库的 `practiceSalesCompany` 配置读取。累计按原付款时点归属的人员主键分组。历史名单、付款和归属有缺漏时显示待核。

负责人和交付分项支持按班次净实收计提，可命名并指定收款人员或组织。适用范围可按新报、复训、销售公司或销售人员限定。需要跟随任职的分项可选择任职组织和方式，只计入任职生效后、结束前的付款。交付阶梯支持用全班净实收选档，再按适用报名的净实收计提。班次计提总额按分舍入，再将尾差分配到报名。订金和尾款按原实付拆分该报名的份额。人员、公司、部门视角可核对同一份草稿。

「外部销售公司提成」适用于直接向公司计提的分项。新报按报名净实收的比例计算，复训可以选比例或每份报名固定额。同一类别的公司共享标准，可单独覆盖某公司的比例或金额。外部公司由实际付款时的公司映射确定收款主体，业绩仍按实际销售人员归属。启用外部公司分项后，同时选择适用个人销售规则的内部公司，未明确配置或映射不唯一的付款列入待核。个人阶梯排除为公司计提的报名，跨期累计使用各班次适用的销售角色和公司规则。

外部公司新报可另设公司推荐比例，并从公司目录选择本版规则可直接收取推荐分润的公司。系统优先使用订单指定的推荐公司，未指定时读取目录当前登记的公司推荐关系。已登记无推荐关系时按零处理，关系缺失、缺少适用的直收配置、收款公司停用或订金与尾款归属不一致时提示待核。推荐分润按一份报名的净实收舍入，按原实付款拆至订金和尾款，并在试算中单列推荐公司的收款。

实战班的复训固定销售提成可按公司拆分。填写销售份额和可选的服务人员份额，余额归入指定资金池。确认名单前发生部分退款且报名仍有效时，保留该公司的固定拆分。拆分按报名计算，并保持订金和尾款各自的应计金额。班次净实收的服务、交付等分项也可归入同一资金池。资金池绑定产品和归集组织，规则引用资金池及分配负责人。财务可在「团队池分配」给原付款时属于归集组织的成员分配，也可登记组织留存。公司、部门和人员汇总读取同一份草稿及其有效分配，合计不因分配而变化。

实战班开放草稿使用最新确认名单。同内容的新名单版本只更新引用。首次名单确认前，已成功且能唯一匹配原付款的部分退款冲减班次试算业绩，比例分润及实付阶梯按净实收计算，仍有效的报名按一人计。固定分项可配置退款处理方式，新报固定销售提成遇到部分退款时须有明确配置。已全退的付款仍在确认名单中时提示核对名单。首次确认后发生且通过付款、产品及累计金额校验的退款在班次中显示为退款账期办理提示，保留班次计提行和已填的团队池分配。关联冲突、累计超额或产品不一致时列为待核。

实战班可按产品登记独立的「退款账期」，当月没有开班也可建立。默认按 25–24 划分，产品可配置开始日。原班次已经确认后，新增退款进退款成功日所属的开放月份。归属月已关账时，进入当前办理月，或沿用此前仍开放的办理月。补同步到的退款如果发生在名单确认前，也按原班次是否已处理判断，防止遗漏或重复。独立计提按结算时使用的规则版本逐笔试算扣减。订金和尾款联动、销售阶梯和班次分润按已结算班次复算，将同一归属月的退款合并处理。试算使用当时的名单、付款、规则和人员归属，结合之前已入账的退款，只扣本次新增差额。明细显示受益人、班次结算期、退款归属期及实际扣减期。账期缺失、已入账退款的关键字段变化或班次结算无法复现时列为待核。

固定账期试算支持成功退款的扣回。分项按计提时使用的规则选择按比例扣回、整笔冲回或不扣回。同账期退款在本期抵扣，历史退款在退款归属期仍开放时进入该期，关账后由当前办理期承接。明细同时显示原受益人、原结算期、退款归属期及实际扣减期。缺少原付款关系、规则口径或已入账退款发生变更时，系统列入待核。

实战班退款账期可由获该产品授权的财务人员在「结算核对」确认。产品默认关闭结算，完成历史数据核对后按产品启用。确认时读取大春之道订单流已完成的同步水位，核对本账期及较早开放退款月的覆盖、关联付款和来源时效。页面显示缺少的同步范围、关联的待结算班次和需要先处理的退款账期。退款账期可以按当期流水关账，团队池剩余余额结转。已确认的后来分配保留，补记扣减形成的负余额由后续归集弥补。班次计提的正式结算仍需完成签到名单接入与上线验收。

实战班在「分润试算」可主动拉取首次和最新确认的签到名单。「结算核对」显示实际使用的名单版本、开班和确认时间、退款分界、订单同步状态及团队池待分配额，并分别提示名单接口未接通、读取未授权和名单有变更。授权财务确认时，系统复核最新试算、订单同步和源端名单。名单有变更时，先到大春之道确认，再重新拉取、试算和核对。财务侧流程已在隔离环境通过，正式启用须接通目标环境的[名单读取接口](docs/contracts/dczd-practice-roster-read.md)并完成真实数据对账。

实战班的「团队池分配」在班次和退款账期使用同一资金池。班次按结束日期排序，退款账期按账期结束日期排序，同日先计班次，再计退款账期。退款归属月早于班次时，当月先记扣减，后续归集再弥补负余额。已确认期的资金池查询使用确认时已入账的前期记录。技术删除错账前核对后续已确认的扣减和结转余额，有依赖时按依赖逆序处理。受影响的开放退款草稿会重新试算。

固定账期内按单计提的推荐分项，使用结算时规则和最新订单版本重新计算，与原入账、已入账差额及退款比较。原结算保留，差额进入可办理的账期。只改订单显示信息时，更正继续归属首次收到财务变更的账期。

大春 AI 按结算时的规则复核成交归属。分项金额和公司、团队池计提核对一致后，按受益人记扣回和补计，金额使用扣除已登记退款后的余额。原订单和原账期使用的规则版本可在「受益人更正明细」查询。归属变化影响分项金额、公司或团队池时，草稿会显示待核。后续退款等待较早账期已经在办理的更正。较早账期的退款按当时已确认的受益人处理。技术重开涉及同一笔计提的已确认差额时，从最后确认的关联账期开始。

实战班在「退款账期」办理已结算订单的受益人更正。以结算时的签到名单、规则和累计起点重算整个班次。同一报名的订金和尾款在不同月份改齐时，差额归最后到齐的办理期。试算列出改归属订单及受阶梯影响的其他订单。已有公司分项发生换收款主体时，分别记原公司扣减和新公司补计。同一团队池的差额按原付款计提行入账，已经确认的分配继续保留。后续退款本金冲减原订单业绩，分润差额按更正后的受益对象核算。缺少原班次累计数据、涉及新增计提分项或改换团队池时显示待核。后续已结算班次的累计档位可能受影响时，工作台提示核对。

待核项显示实际待扣人员、人员编号、金额和原结算期。具备产品结算权限的财务可以登记扣回。核实离职且无法联系时，可选择免扣，正确人员的补发继续计入草稿。确认前复验草稿与待扣金额，随后重新试算。处理选项由数据库配置。

大春 AI 499 支持在工作台确认结算。产品默认关闭确认，按实际对账结果启用。确认后的账期保留一份正式结果，工作台可查其明细和分配结果。

## 本地运行

需要 Go 1.25、Node.js 22、pnpm 10 和专用 PostgreSQL 开发库。首次配置时将 `.env.example` 复制为 `.env.local`，填写本地开发库连接。开发模式使用回环地址和以 `_dev` 结尾的数据库。库名须与 `FINANCE_EXPECTED_DATABASE` 一致。服务启动时初始化表。此配置文件仅保存在本机。

```sh
test -e .env.local || cp .env.example .env.local
chmod 600 .env.local
```

填写后，在仓库根目录启动。

```sh
set -a
. ./.env.local
set +a
go -C server run .
```

在另一个终端启动前端。

```sh
pnpm --dir web install
pnpm --dir web dev
```

前端地址为 `http://127.0.0.1:5176/`，开发代理转发至后端 `127.0.0.1:8096`。`/healthz` 检查 HTTP 服务，`/readyz` 检查开发库连接。

## 财务账号

默认的 `FINANCE_ACCESS_MODE=managed` 要求登录后使用工作台。后端监听回环地址，对外访问由同源 HTTPS 代理转发。仅本机开发库可设为 `development` 来匿名读取和试算开发样本。

账号关联已有的财务人员主键。技术人员使用 `configure-finance-account` 登记账号或调整权限。配置文件可参照下例，人员和产品 ID 使用本平台实际主键。

```json
{
  "login": "finance.operator",
  "personId": 1,
  "enabled": true,
  "workspace": true,
  "organizationWrite": false,
  "rules": [{ "productId": 1, "publish": true }],
  "settlements": [1]
}
```

首次登记或更换密码时，通过标准输入将密码传给 `go -C server run . configure-finance-account /path/to/account.json`。密码使用安全的凭据输入渠道。调整权限或停用时可用 `</dev/null` 保留密码。修改后的配置替换该账号的权限并使既有会话失效。

`workspace: true` 授予全量业务工作台访问，包括全量订单、试算和报表。规则定义的读取和规则发布均按 `rules` 的产品授权校验。`publish: false` 可以查看该产品的规则。发布记录使用当前登录账号主键。从工作台退出会撤销本次会话。

`settlements` 列出该账号可以确认结算的产品主键，需同时具有工作台权限。结算前按当前登录账号重新校验该账期的产品权限。

`organizationWrite: true` 授予组织任职和计提任职维护权，需同时具有工作台权限。普通工作台账号可以查询任职。

## 产品与数据配置

工作台的固定下拉选项由数据库 `configuration_options` 提供，可配置显示名、顺序、是否启用和适用范围。应用从 `GET /api/v1/configuration-options` 读取，初始化仅补入缺少的默认项，不覆盖已有配置。产品、人员和期次从各自的业务表读取。选项编码对应服务端支持的业务行为，改显示名或排列不会修改已经保存的规则。

工作台的「组织与人员」从本平台数据库查询。可按公司、部门、小组或门店筛选直接任职，查看当前归属、指定日期北京时间零点的归属，或全部任职记录。组织树显示当前层级，已停用组织仍可查询任职历史。

授权人员可以登记、调动和结束任职。登记复用已有人员和组织，任职类别由数据库配置。办理调动时，原任职结束时间与新任职生效时间相同，按北京时间执行，已有的计划结束时间随新任职保留。兼任及岗位分别登记。同一人员、组织、类别的任职区间可以相接。每段任职保存最近一次维护的账号和时间。系统标记受影响的开放账期及跨期更正待试算。待确认的团队池分配按原付款时点核对成员资格。班次试算会重新核对报名付款时点和累计阶梯。已结算的报表使用结算时保存的归属。

「组织与人员 → 计提任职」维护大春 AI 的销售资格、项目负责人、团队角色及分配负责人。可以按日期、角色、项目、产品或组织筛选。任职类别和范围类型读取数据库配置。交接在指定的北京时间结束原任职并开始新任职，系统标记对应范围的开放账期待试算。需要唯一负责人的规则会提示重叠任职通过交接办理，销售等多人任职可共存。指定到人的规则按该版配置计提。交接涉及指定受益人时，还需核对该规则的适用版本。团队池分配按原付款时点复查组织成员和计提角色。

技术人员可在专用开发库一次性导入组织数据。文件包含 `capturedAt`、`people`、`units` 和 `assignments`。人员使用 `id` 和 `name`，组织使用 `id`、`parentId`、`name`、`kind`、`status` 及可选的 `sortOrder`，任职使用 `id`、`personId`、`unitId`、`kind`、`position`、`from` 和可空的 `to`。可选的 `companies` 用 `source`、`sourceCompanyId`、`companyId`、`from` 和可空的 `to` 保存来源销售公司标识的有效区间。相同的人员主键与已有人员档案共用，全部记录在单个事务中写入。

可选的 `recommendations` 使用 `companyId`、`referrerCompanyId` 两个公司主键登记已核对的公司推荐关系。明确无推荐关系时填 `"referrerCompanyId": null`。目录变更会标记相关开放草稿重新试算。

```sh
go -C server run . import-organization /path/to/organization.json
```

技术人员可以用核验过的配置文件初始化专用开发库的产品和规则。产品进入产品目录，规则进入「产品规则」，包含适用范围、版本、有效期和暂停状态。日常规则维护使用本平台的授权配置入口。规则状态「未开放试算」表示该规则的计算尚不可办理。

```sh
go -C server run . import-product-config /path/to/product-config.json
```

固定账期配置包含场景映射时，试算页的「订单规则匹配」按实际付款时间查看业务场景及适用规则。同优先级规则重叠时列为冲突。大春 AI 499 的「查看销售分项」根据成交时有效的来源人员、销售公司、费率类别、销售任职和小组归属计算。符合内部拆分条件时，各岗位金额合计与销售总额一致。缺少归属或任职时显示具体待核原因。正式结果在「结算核对」确认后生成。

健康大使和健康创客共用大春 AI 的健康身份订单流。两项产品的 `businessRoutes` 分别配置 `sourceProductCode` 为 `HEALTH_AMBASSADOR`、`HEALTH_CREATOR`。付款和退款按来源产品码进入各自的核算期。健康大使按到账规则试算。健康创客使用付款时的规则和人员归属，在完成账期计入业绩与分润。可以在「订单规则匹配」核对付款与完成日期，在计提明细查实际采用的版本。

健康创客的完成事件补同步时，原完成账期已关账且该笔仍未计提的，补入该产品随后第一个已登记的开放账期。明细显示实际完成日期及「补入本期」，规则和人员归属按付款时点确定。尚无开放账期时，登记后可试算。历史结算从结算明细查实际使用的版本。

完成前发生的退款先减少可计提的实收。晚到完成首次补计时，已关账月份发生且尚未冲回的退款也先减少计提基数。结算后再收到退款时，按退款归属账期办理。归属期已关账的，按当前办理月冲回原受益人和交付池。同步范围须覆盖所用付款。

授权人员可在健康创客的「产品规则 → 分润配置」调整销售费率、各分项比例及规则中指定的个人收款人。人员从本平台档案选择，并按规则生效时间核对计提任职。保存后生成规则新版本，只标记实际使用新版的开放付款账期和完成账期，包括补计账期。正式结算和后续退款引用结算时采用的版本。

已同步的开发库在启用健康身份核算前，按原订单 ID 重拉，或从更早的同步起点补拉，以补齐分类、销售归属和当前完成事件。重拉相同事实会复用已有版本。健康身份的完成事件须关联同一原付款，并通过来源的签署与审核状态校验。来源更正付款或完成状态后，只标记受影响的开放账期。缺少来源产品码的映射可通过重新导入核验后的产品配置补齐。

销售公司在付款时明确登记为未分类时，按规则中的适用公司费率或通用费率计算。用订单已登记的销售归属明确命中 0% 时，销售分润为零，销售分项无需指定收款人。正费率按付款时间核对成交人和销售任职。成交人与订单销售公司有唯一有效的公司成员关系，且当时没有有效销售任职时，个人销售分项显示「付款时销售任职未生效 · 不计提」。来源归属缺失或冲突、费率资料不完整时列入待核。升级后可在工作台重新试算开放账期。

大春 AI 499 的「产品规则 → 分润配置」按分项展示固定比例、费率表和已指定的收款人，可按销售公司、关系或类别筛选费率表。在「内部团队收款人」可查看团队负责人和启用的服务人员分项。具备该产品发布权限时，可从本平台人员档案选择收款人，并与费率调整一起按北京时间发布一版规则。发布时校验新指定收款人和新团队负责人在规则生效时的计提任职。服务人员按规则直接指定。规则记录发布账号，仅标记采用新版的开放账期。订单按付款时点选版，已结算订单的退款扣减引用结算时使用的规则版本。与内部团队拆分联动的销售总费率由拆分规则约束。

工作台使用财务账号会话访问费率配置接口。技术集成可显式配置受信任的签发方，通过 Bearer 调用同一接口。使用 `FINANCE_SESSION_ISSUER`、`FINANCE_SESSION_SECRET` 校验签发，Token 需包含匹配的 `iss`、`aud=finance-platform`、有效的 `exp`、账号主键 `sub`、授权产品 `product_ids` 和 `permission_codes`。可读权限为 `finance.rules.read`，发布权限为 `finance.rules.publish`。

大春 AI 499 可在「分润试算」生成付款与退款草稿。每期只保留一份草稿，明细引用订单版本和适用规则版本。按付款时的有效任职计算负责人分项，公司分润归规则指定的公司，团队池逐笔归集。公司、部门和人员都能查看同一草稿的净业绩、计提和退款扣减，人员视角单列公司及团队池分润。实时匹配页的「团队池归集」显示整个账期的付款归集金额和待核笔数。

会员退款按业务子系统的退款成功日归期，从原付款计提行读取实际费率和受益对象。内部销售按整组剩余金额分配各岗位扣回，并保留各岗位的累计上限。退款扣减明细可回查原结算期、退款归属期和实际扣减期。已入账退款的关键字段发生变化时进入待核。已有只含付款计提的会员草稿会提示重新试算。

试算的「团队池分配」按池显示期初、归集、退款和余额。可从付款时具备成员资格的人员中选择分配对象，输入成员金额或组织留存金额。保存会校验各成员可用的款项并关联到来源计提行。「业绩与分润」显示拟分配金额，汇总总额不变。试算、资格资料或前期结算变化后，原填金额可以复核，过期方案暂停计入汇总。已确认到人的分配发生退款时，扣减回原团队池，池余额不足时由后续归集弥补。

已确认账期的资金池使用确认时已入账的前期流水。补关早期账期后，后续开放账期可结转新的余额。技术删除结算时会核对后续已确认账期引用的期初余额，即使该期没有入池、退款或分配流水。

大春 AI 499 的「结算核对」显示账期状态、来源同步、待核项和各池剩余待分配金额。正余额在确认前完成成员分配或组织留存，负余额由后续归集抵扣。产品完成对账后可启用 `settlement_enabled`。授权财务在确认弹窗核对产品、账期、草稿版本和合计金额。结算事务再次校验最新试算、分配版本及来源覆盖和时效，确认后保留当期付款、退款、分配及规则版本。同一版本与分配重复提交会返回已有的结算。调整早期结算前须检查同一团队池的后续已结算账期。正式启用前须核对团队池期初余额。

可将销售及收益归属资料通过 `import-sales-context` 导入专用开发库。文件包含 `source`、`capturedAt`、`people`、`personLinks`、`companyLinks`、`categories` 和 `appointments`，其中人员链接使用已合并的正式人员主键，类别与任职保留起止时间。计提任职首次在工作台维护后，后续初始化其他销售资料继续使用本平台维护的任职。公司链接的 `unitId` 对应已导入的公司组织主键。可选的 `categoryOptions` 用 `id`、`name` 和 `sortOrder` 初始化费率表类别选项。启用公司与团队池核算时，文件还需要 `organizations` 数组，以 `partyId` 和 `unitId` 关联规则指向的组织主体与本平台组织。

开发验证可使用测试来源接口选取样本。可将 `source` 和 `facts` 写入同一个 JSON 文件，`facts` 为来源接口返回的 `source.order-fact/1.0` 记录数组。在专用开发库可重复导入同一文件。已配置单笔接口的环境可按原订单 ID 查看来源更新。

```sh
go -C server run . import-order-facts /path/to/source-order-facts.json
```

专用开发库可直接读取大春 AI 的会员和健康身份订单流。配置来源地址及服务凭证后，在「来源订单」的「订单同步」中选择对应订单流。首次填写需要覆盖的历史起点，页面会显示排队、读取进度及同步结果。技术命令可触发同一任务。

```sh
go -C server run . sync-dcai-orders VIP_ORDERS 2026-07-25T00:00:00+08:00
go -C server run . sync-dcai-orders HEALTH_IDENTITY_ORDERS 2026-07-25T00:00:00+08:00
```

后续执行可省略日期，继续未完成的水位，或从已完成水位回看 24 小时后同步。已完成的流可以指定更早日期补历史。同一订单流的同步请求共用当前任务和检查点。末页事实、完成水位及任务成功状态在同一事务提交，服务重启后会继续未完成任务。单笔重拉更新该订单和来源状态。结算核对同时检查账期覆盖和同步进度。

已初始化的流按 `FINANCE_DCAI_SYNC_INTERVAL` 自动同步，默认 `30m`。设置为 `0` 可关闭自动触发，手动任务仍可运行。首次接入使用尚未导入大春 AI 样本的专用库。分页和单笔重拉使用同一配置来源，开发样本文件可在单独的样本库导入。结算核对要求同步水位覆盖账期，并使用 `FINANCE_SETTLEMENT_SYNC_MAX_AGE` 检查来源水位与最近一次成功同步时间。默认取一小时与自动同步间隔中的较大值。

大春之道通过同一「订单同步」入口读取订单与退款。设置 `FINANCE_DCZD_URL` 和 `FINANCE_DCZD_TOKEN`，选「大春之道订单与退款」并填写历史起点。首次同步按来源事实进入读取接口的时间取数，订单的付款和退款发生时间按原始数据保存。系统校验来源就绪状态与冲突数，按来源分页上限读取，中断后从已保存的位置续拉。分页与单笔重拉绑定同一来源，首次接入使用尚未导入大春之道样本的库。已初始化的订单流可以通过 `FINANCE_DCZD_SYNC_INTERVAL` 定时同步，默认 `30m`，设为 `0` 时保留手动同步。

```sh
go -C server run . sync-dczd-orders ORDER_FACTS 2026-07-01T00:00:00+08:00
```

实战班在「核算期次」登记来源期次标识，并配置规则和来源产品映射。接通大春之道名单接口后，财务可在「分润试算」手动拉取。技术人员也可将已确认的 `dczd.practice-roster/1.0` 名单导入专用开发库，验证试算。重复导入同一版本会核对内容并复用原记录。计提所需的原付款由大春之道订单流读取。

```sh
go -C server run . import-practice-roster /path/to/roster.json
```

已有关账历史的实战班可以导入冻结的个人累计期初。在专用开发库导入 JSON 后，在实战班新报阶梯的默认累计起点选择相应批次。文件使用 `productId`、冻结结算的 `sourceSettlementId`、`throughAt` 和 `people`。每个 `people` 项带财务人员识别键 `legacyPartyId` 和 `newCount`。首次建立本地人员引用时填入来源的 `displayName`，已有同主键人员可省略。同一个结算的相同内容重复导入会复用批次。

```sh
go -C server run . import-practice-count-opening /path/to/opening.json
```

选用冻结期初后，只将截止时刻之后的已确认新报追加到期初。生效的个人起点按个人窗口重新累计。明确的零期初保留为零，缺少期初记录时显示待核。

```sh
curl --fail http://127.0.0.1:8096/healthz
curl --fail http://127.0.0.1:8096/readyz
go -C server test ./...
pnpm --dir web build
```
